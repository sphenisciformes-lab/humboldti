# 設計

Humboldti Note がなぜこの形なのか。`CLAUDE.md` は規則を述べ、このファイルは理由を述べる。
ここに書かれた理由が成り立たなくなったら、まずこのファイルを更新する。

## 何を作るのか

ターミナルに住む日次メモツール。思いついたことを打てば今日のファイルに入る。
過去の日はカレンダーで辿れる。全体を検索できる。

## 何を作らないのか

- **エディタではない。** Neovim + `render-markdown.nvim` が既にターミナル上の
  マークダウン編集を十分にこなしている。ここで competing しても勝てない。
- **ナレッジベースではない。** Zettelkasten やリンク構造は `zk` と Obsidian の
  領域。Humboldti Note が扱うのは「今日」。
- **VS Code の代替ではない。** 仕事で VS Code を開いている人は、メモツールを
  足しても VS Code を閉じない。省メモリは訴求点にならない。

## 価値の所在

重要な順に3つ。

1. **摩擦ゼロの追記。** `pen <text>` は何も開かずに書き込む。思いつきを
   記録するのにエディタ起動が必要なら、人は記録をやめる。
2. **日本語が本当に動くこと。** 既存の TUI ツールは英語圏で作られ、英語圏で
   テストされている。East Asian Width と IME の挙動は検証されていない。ここを
   正しくやるのは手間がかかり、だからこそ参入障壁になる。
3. **設計上エージェントから読めること。** 既知のレイアウトのプレーンな
   マークダウンなら、Claude Code は統合なしで `grep` と `cat` ができる。
   MCP サーバはその上の利便性であって、本質ではない。

## 保存

```
~/notes/
  2026/08/2026-08-30.md      1日1ファイル
  attachments/               画像。相対パスで参照
~/.config/pen/config.toml
~/.local/share/pen/index.db     再構築可能なキャッシュ
```

**なぜノートを見える場所に置くのか。** `~/.local/share` の下に隠すと、Finder
から開けず、クラウド同期フォルダに置けず、`git init` しづらく、エージェントに
ディレクトリを指し示すこともできなくなる。エージェント連携という強みは、ファイルが
「人間が置きそうな場所」にあることに全面的に依存している。

**なぜインデックスを別の場所に置くのか。** バイナリのキャッシュを `~/notes` の
中に作ると、git のコミットに巻き込まれ、クラウド同期と衝突する。外に出すことで、
ノートディレクトリにはバージョン管理する価値のあるものだけが残る。

**なぜ年月でディレクトリを掘るのか。** 10年分の日次ファイルをフラットに置くと
3,650 個になり、一覧も補完も重くなる。ただしこの構造は利便性であって契約ではない。
探索は `YYYY-MM-DD.md` にマッチするファイルを再帰的に拾うので、ルート直下に
置かれたファイルも動く。

**設定ファイルの場所。** `$XDG_CONFIG_HOME` が設定されていればそれを、なければ
`~/.config/pen/` を使う。`directories` クレートは macOS で
`~/Library/Application Support/` を返すが、これは GUI アプリの作法であって
CLI の慣習には合わない。自前で解決するか `etcetera` の base strategy を使う。

## 追記の挙動

```
## 21:07
最初の思いつき

マージ期間内の2つ目 — 新しい見出しを作らない
```

`merge_window_minutes`（既定 30）以内の連続した追記は、既存の見出しの下に入る。
それを過ぎたら新しい時刻見出しを開く。これがないと、短時間に何度も書いたときに
見出しの壁ができる。

追記は排他ロックを取る。2つのターミナルから同時に追記するのは仮定の話ではなく、
使い始めて最初の1週間で起きる。

前日以前からの繰り越し項目がある日は、時刻見出しをその繰り越しブロックより
**後**に置く。

```
<!-- carried over from 2026-09-02 -->
- [ ] 昨日までの未完了

## 21:07
今日書いた内容
```

見出しを繰り越しの前に置くと「この時刻に繰り越し項目も含めて書いた」ように
読めてしまうが、実際に今日書いたのは見出し以降だけ。見出しを本来の意味の
場所に置き直すことで、繰り越しと今日の新規分の境目も自然にはっきりする
(似た形の `- [ ]` が並ぶと、コメント1行だけでは境目を見落としやすい)。

## 設定

解決順序。上が勝つ。

```
CLI フラグ  >  環境変数  >  設定ファイル  >  Default::default()
```

この階層は `figment` が実装している。自前で書くと、層を追加するときに書き直しになる。

**未知のキーは警告して続行する。** `#[serde(deny_unknown_fields)]` はタイポを
検出できて親切だが、新しいバージョンで書いた設定ファイルを古いバイナリで開くと
起動しなくなる。dotfiles を複数マシンで同期する人が詰む。stderr に警告を出して
処理を続ける。

**既定値は `impl Default for Config` だけに書く。** `config init` はその値を
シリアライズして出力する。コードのどこかに `unwrap_or(...)` の形で既定値を
二重に書くと、いずれ `config init` の出力と実際の挙動がズレる。

## キー

入力は `KeyEvent` のまま画面コードに届かない。先に `Action` に解決する。

```rust
enum Action { NextDay, PrevDay, Open, Search, Quit, /* ... */ }
fn resolve(keymap: &KeyMap, key: KeyEvent, mode: Mode) -> Option<Action>
```

設定ファイルでキーを上書きできる。既定値は `action.rs` のモードごとの表
(`CALENDAR_ACTIONS` など)が唯一の情報源で、`Config::default()` はそれを
呼ぶだけ。

```toml
[keys.calendar]
next_day = ["l", "right"]
```

`KeyMap::from_config` が設定から `(KeyCode, KeyModifiers) -> Action` の表を
組み立てる。存在しないキー仕様や、同じモード内の重複割り当ては起動時エラー
(下記)。`InputChar` は「割り当てのないキーを検索クエリの文字として扱う」
フォールバックであり、設定可能なアクションではない。

キー名はケバブ小文字（`ctrl-a`）。`C-a` や `<C-a>` にはしない。vim 記法は後から
エイリアスとして足せるが、逆は難しい。

同じモードで同じキーに2つのアクションが割り当てられたら起動時エラーにする。
黙って上書きされると、誰にも再現できないバグ報告になる。

## IME

アプリケーションは未確定文字列を見ることができない。macOS の日本語入力が変換中の
文字列と候補ウィンドウを描画し、端末エミュレータが画面を上書きし、アプリには
確定後のバイト列だけが届く。これは Rust の制約ではなく構造的なもので、Vim にも
Emacs にも等しく当てはまる。

ここから導かれる結論。エディタを内蔵しても、`$EDITOR` に任せる場合と比べて
日本語入力の体験は改善しない。一方で**制御できる文字幅の方が実害が大きい**。
そして幅の問題はカレンダー画面と検索画面 — どちらにせよ自分で描くもの — で
発生する。

`/` は IME に食われたり別の文字に変換されたりしうるので、スラッシュで開く
メニューを作る場合は修飾キーによる代替トリガーを必ず用意する。

## エディタの選び方

外部エディタに委譲する方針(前述)は変えないが、どのコマンドを起動するかは
設定の `editor` で上書きできる。`$EDITOR` は Git や他のCLIツールとも共有される
シェル全体の設定なので、Humboldti Note だけ別のエディタを使いたい人が
シェルの設定を汚さずに済むようにするため。優先順位は `editor` 設定 >
`$EDITOR` > `vi`。

GUI エディタ(VS Code など)は既定でコマンドをバックグラウンドに返すため、
`code --wait` のように「ウィンドウを閉じるまで待つ」フラグを利用者が自分で
付ける必要がある。付けなければ `open_in_editor` はエディタプロセスの終了を
即座に検知し、まだ何も書いていない状態を「編集完了」と誤認する。これは
Humboldti Note 側では検知も強制もできない——`git commit` が `$EDITOR` に
`--wait` を要求するのと同じ制約。

## 名前

v1 前に改名した。旧名は打鍵しづらく、2文字級の短いコマンドにできなかった。

プロダクト名は **Humboldti Note**、コマンドは **`pen`**。GitHub は
組織 `sphenisciformes-lab`（ペンギン目の学名）の下にリポジトリ `humboldti`
（フンボルトペンギンの種小名）を置く。将来ペンギン関連の別プロダクトを作る
ことがあれば、同じ組織の下に別の種小名でリポジトリを切る想定。

製品名に **`penguin` という単語そのものは使わない**。Penguin Random House が
「文章を書く」領域(電子書籍・オーディオブック閲覧アプリ等)でクラス9の
"PENGUIN" 商標を複数保有しており、近い領域での使用は避ける。学名の一部である
`Sphenisciformes`/`humboldti` は分類学の用語であり、出版社のブランドとは
別の語彙なので、組織名・リポジトリ名としてこの由来を残しても問題にならない。

コマンド名 `pen` は英語の "pen a note"(書き記す)という表現に掛けている。
